# ADR-009: Automatic rules as JSON lists of conditions and actions

**Status:** Accepted
**Date:** 2026-11-08
**Decision:** One table, `rules` (`migrations/0007_rules.sql`), with `position`, `conditions_json` and `actions_json`. Each JSON column holds a list of objects tagged by `kind` (today `descriptionContains` and `type`; `addTags` and `replaceInDescription`), read and validated by `parseRule` in `src/domain/rules.ts`; the same module decides matching (`ruleMatches`) and which tags a lançamento gets (`tagsFromRules`). The server runs the rules on each new transaction inside `collect/transactions.ts`, in the same batch as its insert, and over the stored ones with the `rules.apply` command; both insert with `ON CONFLICT DO NOTHING`, so a rule only fills empty layers. Text comparison happens in TypeScript, not SQL, because SQLite cannot ignore accents. `replaceInDescription` never writes: the server applies it when it reads a lançamento (`describeWithRules`, called from `lancamentos.ts`), so the bank's description stays as stored in the vault and deleting the rule undoes it; the conditions always look at the bank's description.
**Why:** The owner wants more conditions and actions later (docs/spec/regras-automaticas.md). With tagged unions, a new kind is a new branch in the domain and a new field on the screen, with no migration; the domain stays the single place that knows what a rule means, shared by the app and the server.
**Update (2026-11-08):** `replaceInDescription` no longer runs on every read. The description the rules leave is stored in `transaction_descriptions` (`migrations/0008_transaction_descriptions.sql`), one row only where it differs from the bank's, which stays untouched in `transactions.description`. `server/application/descriptions.ts` computes the rows (`describeWithRules`) and every write that can change them adds them to its own batch: the rule commands (with the rule list as it will be after the write), `lancamentos.categorize` (the category decides the type a condition may look at), `rules.apply` and the collection, for each transaction it inserts or updates. The cron rewrites them all once a day (job `descriptions`), which also filled the table on the first run after the migration. Reads join the table and never load the rules.
**Alternatives:** One column per condition and action (`description_contains`, `tag_id`...): simpler queries, but every new kind needs a migration and the rows fill with nulls. A table of conditions and a table of actions per rule: normalized, but more joins and writes for a list that stays small (at most 200 rules). Matching in SQL with `LIKE`: fast, but case-insensitive only for ASCII and blind to accents.
